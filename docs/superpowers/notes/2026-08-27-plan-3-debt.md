# Plan 3 debt — cleared 2026-08-27

All nine items recorded at the end of Plan 3 are closed. Kept as a record of
what was wrong and why each fix is shaped the way it is; the tests named here
are what stop each from coming back.

## Spec divergences — closed

1. **Spec step 5.3, duplicate provider calls.** The advisory lock was taken in
   the write transaction, after the provider had already answered, so it
   serialised the write and nothing else. Now the pipeline does what the clause
   asks: check, lock, re-read under the lock, then write an in-flight marker
   (`state='pending'` with a fresh `last_attempt_at`) before calling out. The
   marker is what serialises the provider call — `decide()` already reads it as
   "someone is working on this" — so the lock is released before the HTTP call
   rather than held across it, which would pin a pooled connection for eight
   seconds and cap concurrency at the pool size.
   *Chosen cost:* a concurrent duplicate caller gets a 202 with the current row
   instead of its own answer, and the cold path gains one write.
   *Pinned by:* "two concurrent misses for one release make one set of provider
   calls" — deterministic, not a timing race, because the claim transactions
   for a key are serialised by the lock.

2. **Batch misses were not enqueued.** An item that blew its deadline came back
   `pending` with no job row, so the durability guarantee did not cover the
   `items` endpoint — the one the corpus runner uses. Misses are enqueued now,
   but deliberately not continued: a hundred `waitUntil` continuations from one
   invocation would burst the budget the sequential loop protects. Per-item
   `status` is real rather than a hardcoded 200.
   *Pinned by:* "a batch item that blows its deadline leaves a durable job and
   reports 202".

3. **`parsed` differed between POST and GET.** The cache-hit path sent null
   while the poll endpoint sent the stored tokens, so anything aggregating a
   parse rate over responses scored every cached row as unparsed. Carried as
   `cachedParse`, typed as opaque JSON rather than `ParsedVideo` — a refused
   lookup stores `{ refusal }`, so casting the column would be a lie the type
   system could not catch.

## Operational — closed

4. **Cron duration vs sweep size.** `maxDuration = 60` on the route and
   `SWEEP_LIMIT` defaulting to 6. Twenty-five jobs at up to 8s each was 200
   seconds against an unset duration; a cut-short sweep books reclaims as
   attempts, so a job repeatedly at the tail could reach `abandoned` on a stale
   error. Raise them together or not at all.

5. **Reviving an abandoned job kept its exhausted attempt count**, so the next
   sweep spent one attempt and abandoned it again — the safety net was
   permanently dead for that lookup. The reset is scoped to revival; a job
   re-enqueued while still pending keeps its count, or backoff never converges.
   *Pinned by:* one test per direction.

## Minors — closed

6. **`envNumber` duplicated across four modules.** Consolidated into
   `lib/env.ts` as two functions, not one: `envNumber` for legitimately
   fractional values, `envInt` for whole ones. A single naive helper was the
   trap — unify on `parseInt` and `CONFIDENCE_FLOOR=0.75` becomes 0, every
   score clears a floor of zero, and the service marks every lookup resolved
   with no error anywhere. A test pins 0.75 surviving.

7. **Per-job TMDB client rebuilt the token bucket.** One client per sweep now.
   The old arrangement enforced nothing — every job got a full allowance and
   what bounded load was the sequential loop. Built lazily so a missing token
   still throws inside a job's own try rather than stranding its siblings.

8. **The cron test swapped `globalThis.fetch`.** `handleSweep` takes its deps as
   a parameter, mirroring `lookupHandler`, so the test injects a fixture-backed
   fetch. The old form worked but would have left a stubbed global behind for
   the next test file had anything thrown before its `finally`.

9. **`job.category as Category`.** `ClaimedJob.category` is typed properly, with
   the single cast at the row mapper where an untyped column becomes a typed
   value.

## Still open

Nothing from this list. The one thing worth knowing: `readMediaTree` runs on
every lookup response including cache hits, and while it no longer selects the
`raw` payload, it is still three queries per response. If the API ever gets
traffic, that is the first place to look.
